# 用户中心化可行性盘点（Weaveora × MirrorTalk）

> 状态：分析/只读盘点，未做任何代码或库改动。日期：2026-09。来源：两仓库代码与建表 SQL。
> 结论速览：现为**两套完全独立的用户体系**；“统一用户中心”可行，推荐先做 **OIDC/OAuth SSO（B 档）**，不推荐一上来物理合并库。

## 1. 现状事实

| 维度 | Weaveora | MirrorTalk |
|---|---|---|
| 数据库 | `weaveora`（同机 PostgreSQL 127.0.0.1:5432） | `mirrortalk`（同机同库实例） |
| 用户域表 | `users` + `workspaces` + `memberships`(角色) + `credit_wallets` + `credit_ledger` | `users`（单表，无工作区/角色/钱包） |
| users 字段 | id(uuid) / email / display_name / password_hash(Argon2) 等 | id(BIGSERIAL) / email UNIQUE / password_hash(BCrypt) / nickname / avatar / gender / age / bio / traits |
| 认证端点 | register/login/refresh +（代码有 CodeService 验证码雏形） | register/login/login/refresh/forgot-password/verify-code/reset-password |
| JWT | 自签：`weaveora.security.jwt` secret(env)、access 2h / refresh 30d、HS512(如实现为准) | 自签：`JWT_SECRET`(env, HS256)、access 24h / refresh 30d |
| 会话/多端 | JWT 无状态；Weaveora 前端 localStorage | 同（独立实现） |
| 角色 | Membership.Role：OWNER/EDITOR/REVIEWER/VIEWER | users 表无角色列；`ADMIN_ONLY` 仅存在于个别管理接口（AdminService，判定方式需进一步看：疑似配置邮箱或独立机制） |
| 注册副作用 | 注册即建默认工作区 + 送额度(credit_wallets) | 注册仅建 user 行 |
| 规模 | 身份相关 Java ~26 文件；前端 auth 面 4 文件 | 身份相关 Java ~20 文件 |
| 备注 | 内测“非管理员禁建项目”按邮箱 `sysou.com@outlook.com` 判定 | 无此概念 |

**管理员邮箱在两个系统是“名义共享、数据分离”**：Weaveora 的 admin 判定只查 Weaveora.users；MirrorTalk 账号（若同一邮箱）并不自动等于 Weaveora 管理员，除非在 Weaveora 也注册同名账号。

## 2. 统一目标与可选路线

按“要解决什么”选路线（越往下越重）：

- **A 同库复用（轻）**：Weaveora 直接复用 MirrorTalk 的 users/认证（或反过来），其余产品表保留。
  改动：Weaveora 换密码算法/用户来源/注册副作用重定位；难度中；风险：两产品对 users 表的并发语义与字段差异、存量密码哈希不同。
- **B OIDC/OAuth2 SSO（推荐入口）**：授权服务器（先由 MirrorTalk 承担或新增 uCenter 统一入口）签发统一身份令牌；Weaveora 登录改为“授权→换 token→按邮箱映射/创建影子档案”，保留自己的 workspaces/wallet。
  改动：Weaveora 加 OAuth 客户端 + 登录页 + token 映射；MirrorTalk 加授权端点/客户端管理（若无）。可逆、不并库、后续可升级 C。
- **C 独立 uCenter 微服务（彻底）**：身份/资料/钱包/角色收敛到 uCenter，两产品只对接 SDK/API。
  改动：Weaveora identity 整模块下沉+两端接入+数据迁移+灰度；最大。

## 3. 关键差异与风险（迁移时真正的工作量来源）

1. **密码哈希不同**：Argon2（Weaveora）vs BCrypt（MirrorTalk）→ 无法直接拷贝；需“首次登录自动重哈希”或双算法校验过渡。
2. **ID 类型不同**：UUID vs BIGSERIAL → 跨库映射表（email 或 legacy_id）。
3. **Weaveora 注册有业务副作用**（建工作区+钱包+额度）→ 并入 uCenter 后需“首次进入产品时按需初始化”，保持幂等。
4. **角色体系不对称**：Weaveora 有 workspace/membership；MirrorTalk 无 → uCenter 若做角色需兼容“无工作区产品”（角色可为空/全局级）。
5. **验证码/找回密码**：MirrorTalk 有 verify-code/reset 闭环；Weaveora 仅有雏形 → 统一后以谁为准、短信/邮件通道复用。
6. **会话兼容**：两端 JWT secret/算法不同；SSO 化需统一 token 校验源，老客户端（Flutter 发版周期长）需兼容期。
7. **未盘点项（会显著影响人日）**：
   - MirrorTalk 现有用户规模/是否可重建；邮件发送服务（验证码通道）配置；
   - MirrorTalk admin 判定机制细节（AdminService）；
   - Weaveora/MirrorTalk 是否已有手机号登录/绑定（users 表均未见 phone 列，验证码应基于 email）；
   - 部署拓扑是否允许新增 uCenter 实例/域名/证书（现同机 nginx 托管）。

## 4. 工作量粗估（单人，前提：上述盘点项补齐后）

| 方案 | Weaveora 侧 | MirrorTalk 侧 | 合计区间 | 备注 |
|---|---|---|---|---|
| A 同库复用 | 3–5 天 | 1–2 天（配合只读/字段冻结） | 1–1.5 周 | 依赖哈希迁移方案 |
| B OAuth/OIDC | 5–8 天 | 3–5 天（授权端/客户端） | 1.5–2.5 周 | 兼容期按 2 周加 |
| C uCenter | 10–15 天 | 5–8 天 | 3–5 周 | 不含数据清洗/灰度 |

## 5. 建议

1. **目标锚定**：若只需“一套账号登录两个产品”→ B；若还要统一资料/钱包/管理后台 → C（用 B 的授权模型打底）。
2. **先补三项盘点**（只读，半日内）：MirrorTalk 用户存量与 admin 判定、两库 email 是否已存在同名真实账号、验证码/邮件通道现状。
3. **近程可用“邮箱映射”过渡**：不并库先让 Weaveora 管理员判定支持“MirrorTalk 已认证用户同邮箱即信任”，成本极低。
4. 最终方案待补充盘点后形成《迁移设计》（含双写/灰度/回滚）。
