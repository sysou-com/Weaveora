## 1. 用户要的三件事（原话要点）

1. 「每一集如果有已转过的项目，则在『转成项目』按钮旁边增加**查看项目**按钮。」
2. 「如果还点击转成项目，则弹框**红色提示**已有项目；继续则生成项目的**新版本，在项目里面 V+1**。」
3. 「每一集新建或者编辑，哪怕剧情不多**保存都比较慢**，查看是什么原因。」

## 2. 保存慢：真因（实测，不是猜）

线上实测（一次性剧本，已按 id 清理）：

| 步骤 | 耗时 |
|---|---|
| `POST /episodes`（`syncPrevious=false`，纯写库） | **0.01–0.15s** |
| `POST /ai/condensed`（刷新「精简的故事」+ 一致性检查） | **3.7–5.9s**，且随 LLM 延迟/上下文波动（历史日志里见过 **70s**、失败重试 2 次 ~60s） |
| `POST /episodes`（`syncPrevious=true`，老路径） | = 写库 + 上面那次调用（3.8s～70s+） |

**结论：慢的不是数据库，是保存后那次 AI 调用。** 另外老代码把它放在
`@Transactional saveEpisode(...)` **里面** —— 长 LLM 调用占着数据库连接 30–70s，
违反交接纪律 §5.7（Hikari 连接池只有少量连接，多人/多次保存会互相拖垮）。

修法（两层）：
- **前端**：保存只写库（`syncPrevious:false`，立即返回），**后台**再调 `/ai/condensed` 刷新记忆与一致性检查；
  有历史章节改动建议时照旧弹 Q4 确认框；失败只提示、不影响已保存正文。用户看到的结果：保存「秒回」。
- **后端**：`sync=true` 仍保留（接口兼容），但 AI 调用挪到**事务外**，结果另开短事务落库
  （`TransactionTemplate`；`saveEpisodeTx` / `applyCondensedTx`；`aiCondensed` 同样处理）。

## 3. 「查看项目」+ 项目 V+1

- **集 ↔ 项目的唯一关联**是 `briefs.constraints.scriptEpisodeId`（转项目时写入）。
  新增 `BriefRepository.findByScriptEpisodeIds`（native，`constraints->>'scriptEpisodeId' in (…)`）批量反查。
- `ScriptEpisodeResponse` 新增 `projectId / projectTitle / projectRevisionNo`（最新版本号，来自 `prompt_revisions`），
  `listEpisodes` 与保存返回都带上 → 分集行显示 **「查看项目 V{n}」**（点击跳项目页）。
- `POST …/episodes/{eid}/to-project`：若这集已有项目 → **默认沿用同一个项目**，写新 brief + `director.generate` →
  项目里 **V+1**（`nextRevisionNo`）；`ConvertToProjectRequest.newProject=true` 才会另建项目（界面不暴露）。
  类型/画幅/时长/风格是项目级设置，新版本沿用项目本身。
- 前端 `ConvertToProjectDialog`：有已有项目时顶部 **红色 NAlert**（「重复转不会新建项目，会在同一项目生成 V{n+1}」），
  规格项置灰，按钮文案变「在项目里生成 V{n+1}」；分集行按钮变「**出新版本**」。
- `ConvertToProjectResult` 新增 `revisionNo / appended`。

## 5. 待办 / 风险

1. `sync=true` 路径现在是「tx1 写库 → 事务外 AI → tx2 落库」：AI 失败**不会**回滚已保存的正文
   （`refreshCondensed` 内部已 catch 并返回 `source=error`）——这是刻意选择（保存不能被 AI 拖失败），
   但接口语义与旧版「全回滚」不同，已在此记录。
2. `applySync`（用户确认后改历史章节）里仍有一次 `ai.refreshCondensed` 在 `@Transactional` 内 —— 低频路径，未改，留待后续。
3. push origin/master 仍未做（本机与另一台机都有未推送提交）；跨机同步走 VPS `_xfer` 的 bundle 或 origin 的 `wip/script-0917-polish`。
4. 纪律不变：冒烟脚本一律按 id 硬删（含 `shot_drafts → prompt_revisions → briefs → projects` 顺序，`shot_drafts` 用 `revision_id` 关联）；用户数据只读。
