## 4. ⛔ 部署验证抓到的 3 个真缺陷（已修，提交 `191ac2d`）

| # | 缺陷 | 后果 | 怎么发现的 |
|---|---|---|---|
| 1 | `applyTo` 把 `duration_sec` 写成**时间轴绝对终点**而非本镜时长 | 5 镜变 3/6/9/12/15，plannedSec **45s**（目标 15s） | 线上 `/replan` 后查 DB |
| 2 | 归一化「从第一镜开始削」（而非削最长/等水位） | 退化输入被削成 `1/1/1/1/11`（一镜独大） | 修完 #1 重跑 → 观察到 |
| 3 | `status.timingReady` 用了**未归一化**的局部变量 | 老方案被判成「已优化」→ 前端不再自动 replan | 线上 `/runs/status` 返回 `timingReady=true` + `timingMode=shot_fixed` 自相矛盾 |

> 教训：这 3 个都在**单元测试覆盖不到的组合**里（#1 的测试只断言了第 1 镜，恰好掩盖了累加 bug）。
> 已补 2 个回归守卫测试（`applyToWritesPerShotDurationNotCumulativeEnd`、
> `normalizationLevelsLongestFirstInsteadOfStarvingFirstShots`）。**单测 336 项全绿。**

   正确读法：
   ```bash
   ssh sysou "sudo -u postgres psql -d weaveora -x -c \"select gpu_max_resolution, video_params->>'engine' as motion_engine, video_params->>'resolution', video_params->>'frames' from user_engine_settings where gpu_server_url is not null;\""
   ```

   小发现（无公害）：`video_params.num_frames=121` 不在白名单（白名单是 `frames`），会被静默丢弃；
   真正的帧上限来自 API env `WEAVEORA_VIDEO_MOTION_FRAMES_MAX=121`，两者目前数值一致。
