[insight] 出图「某主体的定妆照好像没被参考」的定位法（2026-09-16 夜实测，工具 deploy/diag_face_refs.py）：先别猜提示词 —— 查三处即可分辨「没发出去」还是「发出去但没起作用」：①计划里该主体 portraitAssetId 指向哪张资产；②任务 payload.referenceKeys（槽位顺序）里那张资产在不在；③worker 日志「参考图槽位映射：Picture N = <file>」+ ComfyUI/input 里有没有这个文件（本次三步全过：Picture 3 = cf25253c….jpg = 警幻的定妆照，**确实发了**）。真正的原因在**尺度**：用 /face/probe 量化出图里最大的一张脸 —— 本次第 4 镜（宝玉/可卿/警幻同框）出图只有 **1 张脸能被检出（100px、占画面 1.3%）**，它跟宝玉定妆照的余弦相似度 0.609（= 就是宝玉），而跟警幻/可卿定妆照只有 0.24/0.19（≈ 检不到人）。也就是说：**宝玉的身份锚定生效了，两侧主体的脸小到探针都找不到，看起来就像“没被参考”**。根因是位置框给的是**全身比例**（位置总控「自动分配」默认 w=33~50 / h=100；该镜实为 0.19x0.76、0.17x0.78、0.19x0.65），全身 → 脸必小 → 身份约束基本失效。要保身份：把框改成**半身**（h≈0.45~0.6、y 别太大，脸部占画面 3%+），或把 3 主体同框拆成 ≤2 主体；定妆照本身也应做成近景（本次三张定妆照脸占比都只有 0.025~0.032，本身是半身远景口径）。判据口径：相似度 ≥0.5 基本同一人、<0.3 基本不是同一张脸（insightface w600k_r50）。

[insight] 位置框（区域%）与「脸过小」的实测标定（2026-09-16，含 md5 硬证据）：区域坐标**从不裁/缩图片** —— 送进 ComfyUI 的参考图与库里原件 md5 逐字节一致（实测 221d62…/8219eb…，size 相同）；它只有两个去向：拼进正词（路线A，生效中）、ConditioningSetAreaPercentage 构图条件（默认关）；视频通路完全不读区域，底图只做整帧等比缩放。但它通过**构图**决定脸的大小：实测 框高 h=1.00→脸 47~59px（掉身份，且多主体只检出 1 张脸）、h=0.76→100px（与定妆照相似度 0.609）、h=0.50→138px、h=0.64→166px ⇒ 拟合 **脸宽 ≈ 0.09 × 画幅高 ÷ 框高**（1280x704：h=1.0→63、0.6→106、0.45→141）。阈值：<40px 检测不出｜<64px 红（身份基本失效）｜64~96px 黄｜≥96px 绿（≥112 稳）。位置总控已内置「脸≈NNpx」预告。工具：deploy/diag_face_refs.py（--target 定妆照 + 出图，打印命中数/脸宽/相似度）。

[insight] motion「前几秒快进、3s 后停住、最后又补齐」的根因（2026-09-16 夜，实测）：**不是模型限制，是 worker 降帧判据误判**。同一秒的日志自相矛盾：「卸载完成：可用显存 46.1 GiB」→「显存不足 → 自动降帧：80 → 56 帧（预估需 44.5 GiB > 可用 43.4 GiB，总 47.4 GiB）」→「体检：预估需 44.5 GiB，可用 46.1/47.4 GiB」。43.4 = 总显存 47.4 − 安全余量 4 —— 判据拿「总显存减预留」而不是**刚卸载后实测的可用**去比（46.1 > 44.5，本来完全跑得下 80 帧 = 5.0s）。降帧到 56 帧后出现两个现象：① 整段动作被压进 3.56s（模型会把描述的动作在给定帧数内演完 → 看起来快进 1.4 倍）；② `_retime_to_fps` 按「帧精确」用 tpad **克隆尾帧补到 150 帧** → 尾部约 1.4s 静止。修法：`_fit_budget = 实测 _free（卸载后最准）`，取不到才回退 `total − safety`；降帧日志改成明确写后果 + 建议降分辨率/拆镜而不是降帧。★ 规矩：**降帧 = 静默牺牲时长与速度，不可作为首选方案**；不够时优先降分辨率（保时长/速度），其次拆镜。UI 侧同步改：帧数不再让用户算（默认 = 镜头时长 × 原生 16fps，夹到引擎下发的区间），旁边实时显示「当前 N 帧 ÷ 16fps ≈ X.XXs」，低于镜头时长时红字警告「动作会被压进 X.XXs（看起来快进）、尾部静止补齐」；并写明帧数是**上限**语义（worker 实际取 min(时长×16, 帧数)）：填大无害、填小会压短。

[insight] ★ motion 「被加速/慢动作」的根因与实测标定（2026-09-17/18，全部为**原样重放真实 payload** 的受控实验：同镜第5镜、同首帧、同种子、同多动作提示词、30fps/5.000s/150帧、480p）：
- **第一主因 = 低噪声专家的 lightx2v 4 步蒸馏 LoRA**：`hero`(6步/switch3/cfg3.5/1.0/低噪挂蒸馏@1.0) 每秒 333.7 ↔ **同结构但 lora_low=0（零蒸馏）139.5**（2.4 倍），且耗时 295s → **219s**。机制：该 LoRA 按「4 步定稿 + cfg1.0 + 固定 sigma」训练，我们只给它 3 步且只承担后半段 → 低噪分支「以为只剩最后一步交稿」步子迈得过大，细节阶段反而把动作继续推进 = 观感「冲」。清晰度证据同向：去掉它 6 步就**欠采样变糊**（高频能量 1.35 vs hero 2.47）⇒ **6 步档在零蒸馏下不可用**（要么冲、要么糊）。
- **次级放大器 = cfg**（无蒸馏同族）：cfg 3.5→3.0→2.0 时每秒 239.4 → 220.0 → 141.3（1.7 倍量级）；**补帧不是原因**（不插值 131.5 vs 插值 141.3，仅差 7%，且用户盲判两者都是「慢动作」）。
- **耗时几乎只由总步数决定**（cfg 不影响）：6 步 ≈ 219–295s，20 步 ≈ 488–577s，官方 40 步按外推 ≈ 17 分钟/镜。
- **官方口径**（`wan/configs/wan_i2v_A14B.py` + ComfyUI 官方模板）：`sample_shift=5.0, sample_steps=40, boundary=0.900, guide 3.5`；模板两专家**都挂 4 步蒸馏 LoRA@1.0**、KSamplerAdv steps=4 cfg=1.0 → 官方加速档就是蒸馏档（无 LoRA ≈536s vs 有 ≈97s）。注意 `boundary` 按**时间步**（t≥0.9×1000）切专家，我们 `switch` 按**步序**（非同一语义，勿混）。
- ★ **指标必须两张正交量表**，旧的「整帧像素变化量」**无参考意义**：P4（6步零蒸馏）139.5 与 P2b（20步/cfg2.0，用户判「慢动作」）141.3 几乎相同，但用户实测 P4 **并不慢** —— 根因是该指标把**糊/噪点闪烁**也算成运动。改用 ①**低频相干运动**（先降采样 1/4 + gblur 1.5 再差分，滤掉高频抖动）+ ②**清晰度**（|图 − 高斯模糊| 均值）后，与用户 5 个盲判全部单调一致：hero 207.7/2.47（过快）> P2 155.1（稍正常）> P3 136.6（接近正常）> P4 87.8/1.35（不慢但糊）> P2b 63.6（慢动作）。**仍只能在同镜同提示词内相对比较，跨镜无效。**
- 结论（用户诉求「不蒸馏 + 好动态 + 不冲」）：走**无蒸馏 full 家族 + cfg≈3.0**；**当前生产档**已设为 `{preset:full, steps:20, switch:8, cfg_high:3.0, cfg_low:3.0, lora_high:0, lora_low:0, shift:5, resolution:480p}`（≈8.5 分钟/镜）。**别靠砍步数提速**（12 步以下进糊区），要提速/提质动**分辨率**（官方：显存够就上 720P）。
- ★ **2026-09-20 把 hero/full 改成两个「官方不蒸馏工作点」并写进预设表**（用户要求「选择时直接加载官方参数」）：
  `hero = 20 步 / switch 10 / cfg 3.5/3.5 / lora 0/0 / shift 5.0`（ComfyUI 官方模板质量档，≈8.5 min/镜）；
  `full = 40 步 / switch 36 / cfg 3.5/3.5 / lora 0/0 / shift 5.0`（Wan 原厂 `wan_i2v_A14B.py`：steps 40 / shift 5.0 / guide (3.5,3.5) / boundary 0.9，≈17 min/镜）。
  蒸馏/加速档仍由 draft(4)/balanced(6)/motion(8) 承担（官方加速档另需高噪专家也挂 LoRA，本盒 48G 会 OOM ⇒ 一律 `lora_high=0`）。
  落地三处：`worker/comfy_client.py` MOTION_PRESETS（档位默认）、`user_engine_settings.video_params.preset_snapshots`（UI 切档快照）、`GPU服务器能力搭建指南.md §3.2` 表。

[insight] 导演层口径修正：**「一镜动作多」不算问题，「场景切换过多」才提示**（用户 2026-09-17 明确纠正，**只提示不拦**）：
用户原话：浪花、尖叫、水花**本来就在一个画面同时发生**，不该被当成多次动作去限制（此前我提议的「每镜单动作」提示词硬规则**已取消，未落任何代码**）。真正让观众出戏的是**换场景**。实现：`api/.../director/plan/SceneSwitchNotices.java`（纯函数）+ `GenerateResponse.notices` / `RevisionDetailResponse.notices` + 项目页黄色提示条（`data-testid="plan-notice"`，与「引擎不在线」黄条同款式）。两类判据：① **一镜内换场景** = 单镜文本命中 ≥2 个**不同场景大类**（室内/水域/野外/城市，粗粒度）**且**出现**明确转场用语**（`cut to`/`切到`/`转场`…；刻意不收 `then`/`接着`/`忽然` 这类时序语气词）→ 就是靠「转场用语」这一条保证「海边悬崖+浪花+尖叫」不误报；**运镜多关键帧镜头跳过该检查**（跨帧换空间是设计意图）。② **切换偏密** = 平均 <2.0 秒/镜，或存在单镜 <1.5 秒。硬校验（`DirectorPlanValidator`：镜头数 > ceil(时长/1.5) 直接报错）保持不变；单测 `SceneSwitchNoticesTest` 7/7 通过。
