## 4. 位置（路线 A 生效；两层位置 + 主体点名）

**两层位置**（后端 `JobService.applyLayoutRegions`，优先级从高到低）：

| 层 | 数据 | UI | 语义 |
|---|---|---|---|
| ① 逐镜 | `shots[].layout = [{subject,x,y,w,h}]` | 分镜卡展开 → 「画面位置（本镜）」（可拖拽 + w/h 缩放 + ±1% 微调） | **本镜**位置/远近（w/h 越大=越近） |
| ② 方案级 | `referenceAssets[].region` / `subjects[].refs[].region` | 方案页右卡「位置预览（相对位置 / 区域%）」 | **全片默认**位置（逐镜未覆盖时生效） |
| ③ 点选 | `shots[].lipsync_targets = {subject:{x,y}}` | 预览图点选人脸 | 只有点 → 默认框 0.30×0.45 |

- 归一化 0–1（相对画面宽高），`w/h` 表达**远近与大小**。
- 后端把它们写进 `referenceRegions`（与 `referenceKeys` 同序）**并拼进正词**：
  `Reference image mapping: image1 = 宝玉 (upper-left, x=0.19, y=0.09, box 0.30x0.45); image2 = 可卿 (...)`。
- **`image1` = `referenceKeys[0]`**（= `qwen_image_edit_api.json` 里 LoadImage 节点 `12`，节点按 id 字符串排序取图；`14` = `image2`）。改工作流勿打乱 LoadImage id 顺序。

### 7.3.1 第 4 镜复跑仍串脸 —— 真因（2026-09-16 下午实测）

**先排除误判：位置其实生效了。** 那次成功任务的 `payload.positive_prompt` 尾部原文：

```

主体位置（归一化画面坐标，原点在左上；y 越小越靠上，框越大越靠近镜头）：
  image1 = 宝玉（右上，x=0.73，y=0.16，框 0.19x0.76）; image2 = 可卿（上方，x=0.49，y=0.18，框 0.17x0.78）;
  image3 = 警幻（左上，x=0.00，y=0.00，框 0.33x1.00）。…
```

worker 日志同一次也确认 **3 张参考图全部进了图**：
`refs=f091356a….png, 775813a9….png, 784c40c0….jpg`（3 张、未摘槽）。

**真因：三个主体里只有一个绑了"真定妆照"。** 查该次任务所用确认稿的 `subjects[].portraitAssetId`：

| 主体 | 绑定为"定妆照"的资产 | kind | 快照 subject | 日期 |
|---|---|---|---|---|
| 宝玉 | `…b93bdc0010` | **reference（上传素材）** | (无) | 09-12 |
| 可卿 | `…b961be0012` | **reference（上传素材）** | (无) | 09-12 |
| 警幻 | `…9b826cb60005` | **portrait（生成定妆照）** | 警幻 | 09-14 |
| 袭人 | `…b95b926b000f` | reference（上传素材） | (无) | 09-12 |

即：进模型的 3 张图 = **2 张 09-12 上传的素材图 + 警幻的定妆照**。后端是**故意**尊重这种绑定的
（界面「把所选参考图设为定妆照」= 用户显式指定，不能因为 kind 不是 portrait 就丢掉），
但代价是**参考集风格/构图不统一**（定妆照是标准角色设定图，上传图往往是随手图）
→ 多角色同框时身份互相渗透，表现为「可卿的脸跑到警幻身上」「白衣警幻像没定妆」。

**顺带确认不是别称问题**：4 个主体的 portraitAssetId 互不相同（不存在俩主体共用一张脸）；
方案里也没有"别名重条目"（`PlanSubjects.mergeAliasDuplicates` 已兜住这种情况）。

**已做的改进（本次）**

### 7.4 调研结论：还能怎么提升（候选，未实施）

按「收益/风险」排序，均已核对来源：

1. **白底定妆照把构图带偏** —— 官方/社区最可靠的解法不是提示词，而是 **mask + Inpaint Crop & Stitch**（`lquesada/ComfyUI-Inpaint-CropAndStitch`）：mask 外像素物理上不被改动，从根本上消除白底/证件照残留与整体漂移。代价：要新增节点 + 改工作流结构（属"控制模型级"改动，建议先离线 A/B）。
2. **2511 模板的 `FluxKontextMultiReferenceLatentMethod("index_timestep_zero")`** —— 官方 2511 模板在正/负 conditioning 后各挂一个（2509/Aug 没有）。官方 Note 说「用 Comfy-Org 官方权重可不必，用第三方重打包权重才需要」；我们的 `fp8mixed` 是 Comfy-Org 命名，故**未加**（节点在 GPU 机上确认存在，可随时 A/B）。
3. **`TextEncodeQwenImageEditPlus` 内部一定把参考图缩到 ~1MP**（VL 分支 384²、VAE 分支 1024²、宽高 round 到 8）→ 社区用「输入宽高取 **112 的倍数**（LCM(16,14)）」消除内部重缩放的 zoom 漂移。⚠️ 但本项目「输出画布 = `latent_image` 尺寸」，1280×704 → 改成 112 倍数就会变成 2:1 或 1.75（**画幅会错**），所以**没动**；若将来先把画幅改成 1568×896（1.75，≈16:9）再谈。
4. **多主体同框的社区成功率排序**：(B) 抠图摆位 + Fusion LoRA 一次统一光影 > (C) 分主体 mask + Crop&Stitch 逐次 Edit > **(A) 原生多图 + "image 1 在左 / image 2 在右" 提示词（= 我们现在这条）** > (D) 画笔色块 mask。区域条件/attention-couple 类方案在 Qwen 系**不可用**（Regional Prompter 只支持 SD1.5/SDXL），且 #3 已证明 `ConditioningSetAreaPercentage` 包参考图 conditioning 是核心限制。
5. **负向词在 Qwen-Image-Edit 上基本无效**（社区 CFG 网格实验；架构上没做 CFG 训练）→ 正向描述替代负词；这也解释了为什么"加了很多负词"没效果。
6. PuLID / InstantID / IPAdapter-FaceID **不适用于 Qwen**（是 SDXL/Flux 的 attention patch）→ 别往这个方向投入；要提脸相似度优先「多参考图 + 更高 cfg + FaceDetailer 收尾」。

### 8.5 第 4 镜「张冠李戴 / 位置错位」——真因（问题 5）

用**线上真实任务 payload** 复核（`0a000003-a0a9-1fe7-81a0-a99c09f50069`，第 4 镜，3 主体，17:46 成功），
发现三个可复现的机制问题（都不是“模型不行”）：

1. **槽位命名口径不对（→ 张冠李戴）**
   `TextEncodeQwenImageEditPlus` 内部把参考图拼成 **`Picture 1: <|vision_start|>…`**（节点 `_get_qwen_prompt_embeds`），
   官方 2511 模板与社区写法也都是 `Picture 1 / Picture 2`；而我们正词里只写 `image1 = 宝玉` —— 模型未必能把两者对上。
   → 已改成 **`Picture 1 (image1) = 宝玉 (…)`**（两种口径并列，怎么读都不歧义；`applyLayoutRegions`）。

2. **两套方位互相矛盾（→ 位置错位）**
   同一份 payload 里：镜文案写「警幻…居**后景**自后方追来…宝玉在**前景中央**…可卿在宝玉**右侧**」，
   而用户在位置总控里设的框是 `宝玉 x=0.24 / 可卿 x=0.06 / 警幻 x=0.65` —— **“可卿在宝玉右侧”与 x=0.06（最左）直接相反**，
   “居后景”与 `框 0.33×1.00`（最大框=最近）也相反。模型两头听 → 左右/前后乱。
   → 两头都治：
   - 后端在位置清单后**加覆盖句**：「位置以本清单为准；上文任何方位词若与本清单冲突，一律以本清单为准」
     （英文 `[Authoritative placement] …`）；
   - LLM 侧**禁止再写画面方位**（`director_video_system.md` / `director_image_system.md` / `director_rewrite_shot.md` /
     `DirectorService` 的 SYSTEM_FALLBACK + 生成用户消息 + rewritePrompt 硬规则）：只点名主体 + 写相互关系/动作互动，
     **不写** `left/right/center`、`foreground/background`；已有方位词要求 AI 更新时**删掉**。
     （这一条是对旧 P5 规则的反转 —— 旧规则要求“写明左右与前后景”，正是矛盾源。）

3. **参考图上传失败会静默移位（→ 张冠李戴）**
   worker 旧逻辑：某张参考图上传失败就 `continue`，后面的图**前移一格**，而 Java 侧写死的 `Picture 2 = 可卿` 不会变
   → 该槽装的是第三个主体的脸。
   → 已改为**失败即中止任务**并给出可行动信息（`ComfyError`），并打印实际槽位映射
   `[comfy] 参考图槽位映射：Picture 1 = …, Picture 2 = …`。

4. **（附带）语言混排**：worker 给 Edit 档正词**追加**了一句英文指令，用户把正词改中文后就成了「英文头+中文身+中文尾」。
   → 新增 `_looks_zh()`（与后端 `isZhText` 同口径），追加语**跟随提示词语言**（中文头 + 中文负词）。

**未做（GPU 不可用，留待下一次）**

## 9. 2026-09-16 深夜：项目要交代「年代」+ 剧情主体要有人物档案（P14）

### 9.1 数据模型

**方案级**（`plan.setting`，新字段，向后兼容 = 不存在就不注入）：
```json
"setting": { "era": "清代 · 康熙年间", "notes": "服化道按清代贵族宅院形制（可选）" }
```

**主体级**（`plan.subjects[]` 上扁平新增，空则不写）：
```

age / height / build / personality / appearance   // 自由文本（身高可写 178cm 也可写「高挑」）
```

### 9.2 三处同口径注入（这一步才是「宝玉不再被当女性」的实效所在）

| 去向 | 实现 |
|---|---|
| 导演生成 + 单镜 AI 重写（LLM） | `DirectorService.settingAndSubjectBlock()` —— 两处共用同一份文本（**这是重点**：只喂一处就会出现「导演写少年男性、重写一次变女子」）。`rewritePrompt` 现在会读当前确认稿的方案 |
| 出图正词（每镜/每帧） | `JobService.applySetting()` 追加 `【设定年代/世界观】…`（英文提示词时 `[Setting / era] …`，幂等）；`applyLayoutRegions()` 的槽位清单变成 `Picture 1 (image1) = 宝玉[gender male (男); age 17; build 清瘦; look/costume …]`，并加一句「方括号是固定设定，**不得把男性画成女性**」 |
| 定妆照提示词 | `SubjectPrompts.portraitPrompt(name, kind, refCount, traits)` —— 档案 + 「这个角色是『男』，严重禁止画成女性」 |

**负词**：有 setting 时自动追加 `现代服装/现代建筑/手机/电线/现代交通工具`（Qwen 对负词不敏感，但代价极低且用户能在界面看到）。

### 9.3 「一键生成主体」也产出档案

`SubjectService.ask()` 的 system prompt 现在要求 kind=person 给出 gender/age/height/build/personality/appearance，
并明确「拿不准写 other，禁止臆造」；解析时 `gender` 走 `normGender` 归一（男/male/M → male），
person 缺 gender 时补 `other`（而不是留空让模型猜）。已存在的主体**只补空字段，不覆盖用户填过的**。

### 9.4 用户数据保护（很重要，别删）

`subjects[]`（定妆照 id / 素材图 refs / 别名 / 档案）**全是用户资产，LLM 产不出**。
导演 LLM 在 user 消息里见过主体清单，很可能“顺手”输出一份只有名字的 `subjects` ——
一旦落库，用户配好的定妆照与属性就被洗掉（表现就是「一致性突然全崩」）。
⇒ 新增 `DirectorService.mergePrevSubjectsAndSetting()`：**上一版有 subjects 就以上一版为准（丢弃 LLM 的）**，
