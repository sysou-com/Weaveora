## 5. 数据模型

### 5.1 Flyway `V17__script.sql`

```sql
CREATE TABLE scripts (
  id               uuid PRIMARY KEY,
  workspace_id     uuid NOT NULL REFERENCES workspaces(id),
  created_by       uuid NOT NULL REFERENCES users(id),
  title            text NOT NULL,
  genre            text NOT NULL,                 -- 剧本类型
  characters       text NOT NULL DEFAULT '',      -- 剧本人物及人物介绍
  story            text NOT NULL DEFAULT '',      -- 剧本故事
  conflict         text NOT NULL DEFAULT '',      -- 剧本冲突
  plot_structure   text NOT NULL DEFAULT '',      -- 剧本情节结构
  language         text NOT NULL DEFAULT '',      -- 剧本语言
  stage_directions text NOT NULL DEFAULT '',      -- 舞台说明
  condensed_story  text NOT NULL DEFAULT '',      -- AI 连续记忆：精简的故事
  status           text NOT NULL DEFAULT 'draft', -- draft | writing | completed
  share_status     text,                          -- null=未分享 | pending | approved | rejected
  shared_at        timestamptz,
  created_at       timestamptz NOT NULL DEFAULT now(),
  updated_at       timestamptz NOT NULL DEFAULT now(),
  deleted_at       timestamptz
);
CREATE INDEX idx_scripts_ws ON scripts(workspace_id, updated_at DESC) WHERE deleted_at IS NULL;
CREATE INDEX idx_scripts_share ON scripts(share_status, updated_at DESC)
    WHERE share_status = 'approved' AND deleted_at IS NULL;

CREATE TABLE script_episodes (
  id           uuid PRIMARY KEY,
  script_id    uuid NOT NULL REFERENCES scripts(id),
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  episode_no   int  NOT NULL,
  title        text NOT NULL DEFAULT '',
  content      text NOT NULL DEFAULT '',
  summary      text NOT NULL DEFAULT '',          -- 本集摘要（供精简故事/后续生成）
  ai_polished  boolean NOT NULL DEFAULT false,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT uq_script_episode_no UNIQUE (script_id, episode_no)
);
CREATE INDEX idx_script_episodes_script ON script_episodes(script_id, episode_no);

-- 「记录之前章节哪些地方有改动」
CREATE TABLE script_changes (
  id               uuid PRIMARY KEY,
  script_id        uuid NOT NULL REFERENCES scripts(id),
  episode_id       uuid,                          -- 触发者（可空=字段/要素更新）
  episode_no       int,
  kind             text NOT NULL,                 -- episode_create|episode_update|condensed_refresh|consistency_fix|field_update
  changed_episodes jsonb NOT NULL DEFAULT '[]',   -- [{episodeNo,title,what}] 受影响的既有章节
  note             text NOT NULL DEFAULT '',
  actor            text NOT NULL DEFAULT 'user',  -- user|ai
  created_at       timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_script_changes_script ON script_changes(script_id, created_at DESC);

-- 剧本集市点赞/收藏（镜像 project_marks）
CREATE TABLE script_marks (
  script_id   uuid NOT NULL REFERENCES scripts(id) ON DELETE CASCADE,
  user_id     uuid NOT NULL REFERENCES users(id)   ON DELETE CASCADE,
  kind        text NOT NULL CHECK (kind IN ('like', 'fav')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (script_id, user_id, kind)
);
CREATE INDEX idx_script_marks_kind ON script_marks(script_id, kind);
```

Entity 写法沿用仓库既有风格：`@Entity` + `@UuidGenerator(TIME)` + 静态 `create(...)` 工厂 + 只读 getter；
集为**硬删除**（避免软删与 `uq_script_episode_no` 冲突），删除后后端重排 `episode_no`。

## 6. API 契约（`/api/v1/scripts`，均需 `X-Workspace-Id`）

### 6.1 剧本 CRUD

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/scripts?page=0&size=8` | 我的剧本分页（updated_at DESC） |
| POST | `/api/v1/scripts` | 新建（title/genre 必填，其余可空） |
| GET | `/api/v1/scripts/{id}` | 详情（8 字段 + 精简故事 + 计数） |
| PATCH | `/api/v1/scripts/{id}` | 更新任意字段（局部） |
| POST | `/api/v1/scripts/delete` | 批量软删 `{scriptIds:[]}` |

> 对齐项目模块：`GET /api/v1/scripts` 仍返回数组（内部用）；**分页走 `GET /own`**；
> 另外新增集市端点（§6.4）。

### 6.2 集

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/scripts/{id}/episodes` | 集列表（含正文，按 episode_no ASC） |
| POST | `/api/v1/scripts/{id}/episodes` | 新增一集 `{title, content, aiPolished, syncPrevious:true}` → 返回 `{episode, condensedStory, changes[]}` |
| PATCH | `/api/v1/scripts/{id}/episodes/{eid}` | 更新一集（同上带回同步结果） |
| DELETE | `/api/v1/scripts/{id}/episodes/{eid}` | 删除一集并重排编号 |
| GET | `/api/v1/scripts/{id}/changes?limit=50` | 变更记录 |

### 6.3 AI

| 方法 | 路径 | 请求 | 返回 |
|---|---|---|---|
| POST | `/api/v1/scripts/{id}/ai/field` | `{field, mode:'from_title'\|'from_content', hint?, currentValue?, apply:true}` | `{field, value, note, changed, applied}` |
| POST | `/api/v1/scripts/{id}/ai/next-episode` | `{polished:true, titleHint?, instruction?, episodeNo?}` | `{episodeNo, title, summary, content, source}` |
| POST | `/api/v1/scripts/{id}/ai/condensed` | `{}` | `{condensedStory, conflicts[{episodeNo,title,issue,fix}], completedBeats[]}` |
| POST | `/api/v1/scripts/{id}/episodes/{eid}/apply-sync` | `{items:[{episodeNo, content?, summary?}]}` | `{changes[]}`（Q4：确认后才应用） |
| POST | `/api/v1/scripts/{id}/ai/guide` | `{}` | `{stage, missingBeats[], suggestions[], estimatedRemainingEpisodes}` |

`mode:'from_title'` 只注入 标题+类型；`mode:'from_content'` 注入 8 要素 + 精简故事 + 已写集数的标题/摘要
（正文按最近 N 集 + 每集截断，控制上下文）。`source` = `llm | stub`，与现有 `DirectorLlm.source()` 同口径。

（上限 20000，`constraints.source='script'` + `constraints.scriptEpisodeId`），
使「每集内容与标题」真正带入项目；`condenseBrief=true` 时先调 AI 压到 ≤1800 字再写入。
项目要素（画幅/时长/风格/每镜）来自弹框，其余沿用 `CreateProjectRequest` 校验（时长 ≤300s）。

## 7. AI 设计

### 7.1 复用与扩展

- 复用 `DirectorLlm.generateJson(LlmRequest)`（OpenAI 兼容，`max_tokens=8000`，超时 60s，`StubDirectorLlm` 离线兜底）。
- `ScriptPrompts.java` 为**提示词单一真源**（系统词 + user 组装 + Stub 兜底文案）；
  系统词同时落 `api/src/main/resources/prompts/script_{field,episode,guide}_system.md`，两处必须同口径（沿用现有铁律）。
- 所有 AI 返回**只接受 JSON**，解析失败按现有 `DIRECTOR_PARSE_FAILED` 口径重试 1 次再报错。
- **用户数据不被 LLM 覆盖**（沿用铁律 ④）：AI 只产出「值」，由 Service 决定写不写；要素/集由用户确认后落库。

### 7.2 字段生成（`from_title`）

```
你是资深影视编剧与剧本医生。用户给出剧本标题与剧本类型，请只针对指定字段写出专业内容。
字段：{fieldLabel}
字段说明：{fieldHelp}
硬要求：
1. 长度不少于 4000 个中文字符（**硬要求**，不足则继续写具体细节，禁止凑字式空话）；
2. 与剧本类型/题材一致；人物要立体（性格/背景/动机/目标/人物关系）；
3. 可用小标题、分条、表格化文本组织，便于编剧直接使用；
4. 不得与标题/类型矛盾。
只输出 JSON：{"field":"{field}","value":"...","note":"一句话说明"}
```

### 7.3 字段更新（`from_content`）

```
你是这部剧的剧本医生。下面是该剧**已确立的全部内容**（要素 + 已写集数）。
请据此重写并更新字段「{fieldLabel}」，使其与已完成章节**完全一致**、不产生矛盾。
要求：长度不少于 4000 字；保留原有可取内容，标注你新增/修正了什么。
只输出 JSON：{"field":"{field}","value":"...","changed":true,"note":"新增…；修正…"}
```

### 7.4 下一集（`ai/next-episode`，polished=true）

```
你是本剧编剧。请依据「精简的故事」（连续记忆，唯一事实来源）、剧本要素、以及最近几集，写出**下一集**。
硬要求：
1. 严格承接精简故事中的既有事实：人物性格/关系/动机/已发生事件/伏笔与年代设定，均不得矛盾；
2. 按「剧本情节结构」判断当前处于 开端/发展/转折/高潮/结局 的哪一段，并据此安排本集功能；
3. 本集必须有明确冲突（人与人 / 人与环境 / 人物内心），有推进、有转折，结尾留钩子；
4. 语言遵守「剧本语言」风格；对话与舞台说明分开书写；
5. 正文不少于 {minChars} 字（默认 4000），不多于 8000 字。
只输出 JSON：{"episodeNo":n,"title":"...","summary":"<=120字","content":"..."}
```

### 7.5 精简故事刷新 + 一致性检查（保存集时自动触发）
```
你在维护这部剧的「精简的故事」——它是唯一的连续记忆，供后续每一集生成使用。
输入：现有精简故事；全部要素；全部已发布集（编号/标题/摘要/正文节选）。
任务：
1. 重写精简故事：按时间顺序保留所有已确立事实（人物关系、已发生事件、伏笔与未回收钩子、场景与年代），
   去掉文学描写，压缩到 {maxChars} 字以内；
2. 找出既有集之间、或集与要素之间的矛盾/断裂，**列出受影响的既有集**及需要修改的要点（无则空数组）；
3. 标注情节结构已完成的部分。
只输出 JSON：{"condensedStory":"...","completedBeats":["开端","发展"],
  "conflicts":[{"episodeNo":2,"title":"...","issue":"...","fix":"..."}]}
```

保存流（**Q4 先确认再改**）：
`保存集 → 刷新精简故事 → 返回 conflicts[] 给前端 → 前端 SyncConfirmDialog 让用户确认 →
POST /episodes/{eid}/apply-sync {items:[{episodeNo, applyContent, newSummary}]} → 应用改动 + 写 script_changes → 返回 changes[]`。
未确认时不改任何历史章节，只把 `condensedStory` 与建议写入 `script_changes`（`kind=consistency_proposal`）以备查。

### 7.6 AI 引导（`ai/guide`）

```
基于精简故事与「剧本情节结构」，判断剧本走到哪一步，给出下一步该怎么写。
只输出 JSON：{"stage":"发展","missingBeats":["高潮","结局"],"suggestions":["…","…"],
 "estimatedRemainingEpisodes":4}
```

## 8. 关键用户流程

### 8.1 新建 → 详情
`我的剧本` →「新建剧本」→ 填标题/类型 → 逐字段「AI 生成」（或一键全生成）→
可「AI 更新」按整体内容重写 → 保存 → 跳 `剧情详情`。

### 8.2 开始下一集
`剧情详情` →「开始下一集」→ 弹框（是否 AI 润色）
- **要**：`POST /ai/next-episode {polished:true}` → 标题+正文回填编辑器（可改）→ 保存
- **不要**：直接给空编辑器 + 自动标题「第 N 集」
保存前二次确认：「保存后 AI 将自动更新《精简的故事》，并检查/更新前面章节。」
保存 → 后端刷新精简故事 + 一致性 → 返回 `changes[]` → 前端提示「已同步更新：第2集…」+ 变更记录。

### 8.3 AI 引导与收束
`AI 引导` 卡片常驻：当前阶段 / 缺失结构 / 建议 / 预计还需集数；点建议可直达「开始下一集」。

### 8.4 转成项目
某集 →「转成项目」→ `ConvertToProjectDialog`（类型/画幅/时长/每镜/风格/AI 精简开关）→
`POST …/to-project` → 建项目 + brief + 导演生成 → 返回 `{projectId, revisionId, shotCount}` →
跳 `/app/projects/{projectId}`（现有分镜台，可见每镜 `action` + 正/负提示词）。

## 12. 上线实测后的实现口径（2026-09-17，以线上为准）

以下四点都是**上线跑真实 DeepSeek 才暴露的**，已固化为实现口径；改这部分前请先读完本节。

### 12.1 「≥4000 字」必须**分段续写**，不能一次要（否则必 422）

- 现象：单次要求「不少于 4000 字」→ LLM 输出超出 `max_tokens=8000` →
  `finish_reason=length` → 网关重试两次仍截断 → `DIRECTOR_PARSE_FAILED`（422，实测耗时 92s）。
- 口径：`ScriptPrompts.FIELD_PASS_CHARS = EPISODE_PASS_CHARS = 2200`、`MAX_PASSES = 3`、
  `MAX_SEGMENT_CHARS = 2600`（提示词里的硬上限）。每段独立调用，拼接后在总量上满足 ≥4000；
  常规两段（≈4400 字）即达标。续写段必须注入**已生成前文的尾部（1400 字）** +「不得重复」+「不要总结」+「不要在本段把整集收尾」。
- 实测产出：字段 5232～5725 字（约 90～135s）、一集 4054～5565 字。
- 配套韧性：某一段调用失败/返回空正文时**不得丢掉已生成部分**（`retryBlank` 先明确要求「必须给正文」重试一次，
  仍失败或已无预算则 `break` 并如实告知用户）；
- 前端因此需要长等待：已提示「1–2 分钟请勿关页」，且「一键生成全部」改为**并发 3 路**（串行 6 字段会要十几分钟）。
- 相关接口超时：`weaveora.llm.timeout-sec` 默认 60s（单段足够）；nginx `/weaveora/api/` 已 `proxy_read_timeout 1800s`。

### 12.2 长中文段落的 JSON 会被写坏 → `JsonGuard` 兜底修复

- 现象：模型在 `{"value": "第一段\n第二段"}` 里直出**真实换行** → `readTree` 报
  `Unexpected character ('豪'): was expecting comma to separate Object entries` → 重试仍失败 → 422（内容其实是对的）。
- 口径：`infra/llm/JsonGuard.repairStrings()` 在网关剥围栏后、校验前修字符串内的裸控制字符；
  真的结构损坏（少括号）仍会失败（不掩盖真问题）。单测 `JsonGuardTest`（8 例）。

### 12.3 返回的键名不能只认一个

- 现象：模型偶尔把正文放在 `text`/`body`/`value` 下，或写成子对象；
  早期实现只读 `content` 得空串 → 抛 BizException 且**无任何日志**（排障只能猜，违反「不要静默丢东西」）。
- 口径：`ScriptAiService.pickText()` 依次尝试 `content/value/text/body/paragraph/正文/内容` → 再递归查子对象 →
  都找不到才失败，并打日志带**顶层字段名 + 原文开头 320 字**。提示词也统一成固定结构（每段都返回 title/summary/content）。

### 12.4 验收结果

生产环境一次性数据跑完整链路，**19/19 通过**：字段生成 5725 字 / 下一集 5565 字 / 精简故事+变更记录 /
AI 引导 / 转成项目（6 镜 `action` 与 `positive_prompt` 均非空，内部 brief 780 字）/
分享→待审→审批→游客可读→只读集列表。数据跑完已清理（`scripts` 归零）。

### 12.5 【A】输入侧上下文预算（2026-09-17 第二轮）

背景：六要素最大 8000×6 ≈ 4.8 万字。实测（直打 DeepSeek）：**1 汉字 ≈ 1 token**；
30 万 token 输入**不报错**（上下文 ≥30 万）——所以超长**不会失败**，但会：①每段都重送一遍（成本/延迟膨胀）、
②「中间丢失」导致约束被忽略（隐性质量问题，比报错更难发现）。

口径（`ScriptPrompts.context()`）：

| 项 | 预算 |
|---|---|
| 总上下文 | **12000 字**（≈12k token）封顶 |
| 标题/类型 + 精简的故事 | 必留（≤1500） |
| **目标字段** | 全文（≤8000） |
| 其它 5 个要素 | 摘要「头 60% + 尾 40%」，≤1200 字/项；预算不够继续压，低于 260 字则整项省略 |
| 集列表 | 标题+摘要**全量**；正文只给**最近 2 集**（各 ≤1200） |

被压缩/省略的项**记 INFO 日志**（不静默）：实测日志形如
`字段「剧本冲突」 上下文已按预算裁剪（12000 字上限）：压缩「剧本故事」→ 982 字；…`。

### 12.6 【B】结构先行：提纲驱动分段

流程：`目标字数 → planFor(target) 得段数 N → 先要一份 N 段提纲（每段 2–4 个子要点）→ 第 K 段只写提纲第 K 条`。

- 好处：不跑偏不重复、段落边界由提纲确定、可向用户展示「本次 AI 提纲」（字段 diff 弹层与分集抽屉均已展示）；
- 提纲失败**不阻断**正文（退化为按段数自行推进，只记一条 warn）；
- 分集另有「本段功能」提示（起 / 承转 / 合+钩子）与提纲并行；
- 接口：`AiFieldResult.outline` / `AiNextEpisodeResult.outline`（每段一行字符串）。

### 12.7 【C】全剧记忆参与所有调用

「精简的故事」（≤1500 字）作为**最高优先级上下文**注入字段生成 / 分集生成 / 一致性检查 / AI 引导；
为空时显式写「（尚无——本剧还没有已完成的集）」，不让模型猜。它同时承担「整体结构/大纲」的角色。

### 12.8 字数弹窗（用户设定每个要素的长度，上限 8000）

- 点「AI 生成 / AI 更新」/「一键生成全部」→ 先弹 `ScriptLengthDialog`：500–8000（NInputNumber + 滑块 +
  预设 1000/2000/4000/6000/8000），并用 `localStorage` 记住上次值；弹窗内直接显示预估耗时（段数×30–45s）。
- 后端 `targetChars`：`@Min(0) @Max(8000)`（>8000 归 400）；服务层再 `clampTarget` 夹到 500–8000；
  分段数由目标算（`planFor`），每段 ≤2600。
- 实测：1200→1329 字/19s（1 段）；8000→8925 字/96s（4 段，且因上下文变小而快于此前 4000 字的 135s）。
