## 2. 真因（按线上 jar 反编译逐行核对，不是猜）

日志铁证（08:44 那次，用户目标 500 字）：

```
08:44:28  剧本 AI（第 1 集第 1 段）…      ← 第 1 段
08:44:34  剧本 AI（第 1 集第 2 段）…      ← 竟然还有第 2 段
08:44:50  第 1 集 写超（1335 字 > 目标 500 字），已压缩到 473 字   ← 就是那句「AI 生成内容超长」
08:46:00  script episode saved            ← 前端总等待 ≈ 1.5–2 分钟
```

`ScriptAiService.nextEpisode` + `ScriptPrompts.planFor` 的三处口径打架：

| 位置 | 旧行为 | 后果 |
|---|---|---|
| 计划段数 | `passes = clamp(ceil(目标/2200), 1, 5)`，500 → **1 段** | 提示词里写「会被拆成 1 段」 |
| 循环上限 | `min(5, passes + 1)`，500 → **2 段** | 实际写 2 段 |
| 每段预算 | `perPass = clamp(ceil(目标/passes), 400, 2600)`，500 → **500 字（=整集量）** | 每段被要求「约 500 字、严格不超过 800 字」→ 2×≈670 = **1335 字** |
| 早停判据 | `acc.length() >= EPISODE_MIN_CHARS(4000)` | 与用户小目标**脱钩**：够了还继续写 |
| 压缩触发 | `len > 目标 × 1.5`（500→750），而单段封顶是 `max(800, 目标×1.3)=800` | **老实按提示词上限写完也会被判写超** → 多一次压缩 LLM 调用 + 弹「写超了…」 |

即：**目标越小越必然超字**（800 > 750 的封顶 vs 阈值的矛盾），于是必然多一次压缩调用 —— 与「字少应该更快」正好相反。
